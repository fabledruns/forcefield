## Executive Summary

Since the RECONCILIATION baseline (`e65d990`, 68/100, NOT YET), the two
structurally most important gaps have narrowed: there is now a real
supervision story (`ff supervise` repeatedly runs `ff run --resume` on the
same session, bounded by `--max-restarts` with backoff, restarting only on
`ExitRetryable`, with restart lifecycle persisted in the session file), and
there is now a real local MCP stack with enforced frame/tool/schema bounds,
fail-dead crash semantics, and extensive hermetic tests. The old quick wins
also landed: `resource_exhausted`/`insufficient_quota` are quota phrases
(`internal/providers/retry.go:107-119`), and `ff chat --resume` no longer
silently starts a new session (`cmd/chat.go:27-54`).

The system is still not demonstrably safe for 120 hours unattended. Three
P1s carry the verdict: (1) mid-run session-save failures are swallowed
(`_ = sess.Save()` throughout `internal/recovery/driver.go` and
`supervisor_state.go`; only the *final* save is gated in
`finishResumeSession`), so a disk-full/permissions/AV-lock event mid-run
produces silent memory/disk divergence with a stale supervisor budget;
(2) `ff run` (non-resume) exits 0 on unverified `partial` outcomes, so an
orchestrator cannot distinguish success from unverified output; (3) live
shell-stream chunks bypass the 2 MiB result cap, giving chatty processes an
unbounded channel into TUI transcript growth. Around those sit eight P2s
(env-key validation gap with a divergent WSL code path, interactive-command
heuristic bypasses, missing sensitive-escalation for foreground `shell`,
silent auth-header override, no global rate limiter, trickle-body timeout
gap, uncapped per-operation session-allow growth, diagnostic file-count
growth without GC) and eleven P3s. Two of the P2s (secret leakage through
both permission surfaces) are fixed in this audit with proven regression
tests. One headline suspect from the deep trace — a per-agent
`system_prompt` override bug in `effectivePromptFor` — was refuted by
tracing the registry-merge path and is recorded as benign dead code, with
the existing end-to-end test cited.

Verdict: **NOT READY** for 5-day unattended operation. The supervised path
(`ff supervise` under an external process supervisor, strict sandbox config,
watched disk/billing) is now the credible route, but the P1s above must
close first, and race coverage for this commit must be re-established.

## Findings

### [P1] Mid-run session-save failures are silently swallowed

**Location**

* `internal/recovery/driver.go:27,40,79,92,96,100,105,109,126,143,161,165,169`
  — every `_ = sess.Save()`
* `internal/recovery/supervisor_state.go:25,39,50` — `_ = sess.Save()`
* Mitigating gate (final save only): `cmd/run.go:206-210`
  (`finishResumeSession` checks `sess.LastSaveError`)

**Problem**
The driver persists after every meaningful event (heal, tool start/finish,
terminal handling, assistant-text flush) but discards every save error.
`LastSaveError`/`LastSaveTime` are recorded (`internal/session/manager.go:62-64,85-91`)
yet never consulted mid-run. A disk-full, read-only, AV-locked, or
quota-exceeded session file mid-run means memory advances while disk goes
stale — silently. Worse, `SuperviseFrom` resumes its restart budget from
persisted supervisor state (`supervisor_state.go:14-26`); a stale `Restarts`
value permits extra restarts beyond budget.

**Failure scenario**
Day 3 of an unattended run: disk fills (traces + sessions + tool outputs).
The session file stops updating; the run continues in memory for hours,
executing tools. On the next process restart, recovery heals from a
day-old session: completed work is re-planned and tools with side effects
are proposed again (recovery itself never re-executes, but the *model*,
seeing stale history, re-issues the calls). Supervisor budget reads stale
`Restarts` and over-restarts against a struggling provider.

**Impact**
Silent state divergence; possible duplicate side effects after recovery;
supervisor budget bypass. Directly violates requirements 5 (corrupted
persistent state), 8 (silently lose work), and 10 (recover without human
intervention).

**Evidence**
Quoted pattern repeats 12+ times, e.g. `driver.go:38-40`
(`sess.AddPendingCall(call); _ = sess.Save()`) and
`supervisor_state.go:24-25`
(`sess.Supervisor.Restarts = restarts; _ = sess.Save()`). The only gate is
the terminal one in `finishResumeSession` (`cmd/run.go:206-210`), which
does not help a run that continues for hours after the first failed save.

**Fix**
Check the save result at persistence points that advance lifecycle state:
abort the run to `EventError` (non-transient, human-visible) when a save
fails after tool execution or terminal handling, or at minimum surface a
sticky `save-degraded` flag that (a) blocks further tool execution,
(b) forces the exit to non-zero, and (c) is rendered by `/status` and the
supervisor. Persist supervisor `Restarts` increments with a verified save
before consuming budget.

**Regression test**
Hermetic: inject a failing session store (read-only dir / full disk stub)
mid-run, assert the run stops executing further tools and exits non-zero
instead of continuing in memory. Also assert `SuperviseFrom` does not
consume budget on an unverified restart write.

**Confidence**
High.

### [P1] `ff run` exits 0 on unverified `partial` outcomes

**Location**

* `internal/recovery/exit.go:74-77` (`Classify`: `EventDone → ExitOK`
  unconditionally)
* `internal/runtime/runtime.go:2013-2018` (`EventDone` emitted with
  `Status` attached but `RunContext` returns only `Response`)
* `cmd/run.go:112,126` (prints `response.Content`, returns nil)

**Problem**
Verification state (`verified` vs `partial` vs none) is computed
(`task/state.go:226-248`) and attached to the terminal event, then dropped
on the floor: exit code and stdout are identical for verified and
unverified completions. An unattended orchestrator (or `ff supervise`
parent, or CI gate) cannot distinguish "task verified" from "model stopped
talking."

**Failure scenario**
A 5-day goal requires a migration to be tested. The model finishes with
"done, tests pass" but never ran anything; `Status` is `partial`; `ff run`
prints the claim and exits 0. The supervisor parks (code 0 is terminal),
and the pipeline promotes unverified work.

**Impact**
False success reporting — requirement 9 violated at the process boundary.
This is the exact "model claim mistaken for fact" hole the audit brief
centers.

**Evidence**
`exit.go:75-77` returns `ExitOK` for `EventDone` without inspecting
`Stats` or status. `RunContext` (`runtime.go:1850-1856` region) returns
`Response` on `EventDone` without checking `Status`. `run.go:112` prints
content only.

**Fix**
Decide the contract explicitly: either (a) map `EventDone` with
non-`verified` status to a distinct non-zero exit (e.g. extend the 2/3/4
contract) with stdout/stderr clearly labeled, or (b) print a
machine-readable outcome line (status + verification) that supervisors
parse. Document the choice in `docs/Recovery.md` and `docs/CLI.md`. Note
plain-chat (zero tool calls) legitimately reports `verified` with
`VerificationNone` (`task/state.go:242-246`) — the contract must say so.

**Regression test**
`ff run` stub emitting `EventDone` with `StatusPartial` must exit non-zero
(or emit the outcome line); `EventDone` with `StatusVerified` must exit 0.
Pin plain-chat `verified` behavior so the fix does not break chat usage.

**Confidence**
High.

### [P1] Live shell-stream chunks bypass the output cap (TUI transcript growth)

**Location**

* `internal/tools/shell/shell.go:612-631` (`streamPipe`: `dst.append`
  caps, `onChunk` emits uncapped — verified current code)
* Consumers: scheduler progress events (scrubbed, never capped);
  headless driver drops progress (`internal/recovery/driver.go:220-221`,
  "display-only: never …"), TUI transcript accumulates.

**Problem**
The 2 MiB result cap (`DefaultShellMaxBytes`) bounds only the accumulated
`Result`. Every line is additionally forwarded uncapped over `onChunk`.
In TUI-attached runs each chunk becomes transcript content with O(n)
rebuild cost per event (pre-existing TUI behavior). A chatty process
(`tail -f`, `yes`, verbose builds, `find /`) over hours produces unbounded
transcript memory and UI stall. Headless `ff supervise` runs are largely
spared (driver drops progress events), which bounds the 5-day impact to
TUI-attached operation — hence P1 rather than P0, but a supervisor
operator watching via TUI still hits it.

**Failure scenario**
Unattended TUI session runs a log-tailing or verbose-build command; over
36 hours the transcript grows to hundreds of MB; rendering stalls; the
operator cannot intervene because the UI is unresponsive; memory pressure
affects the whole process.

**Impact**
Resource exhaustion in long-lived TUI sessions (requirements 2, 10).
Headless: wasted CPU/bandwidth on the event channel only.

**Evidence**
`shell.go:619-623`: `dst.append(stream, line)` then unconditional
`onChunk(...)`. No byte/line/event counter on the stream path. Jobs are
not affected (`jobs.go:290-291` passes nil chunk).

**Fix**
Bound the stream path: cap total streamed bytes per execution (e.g. share
the result budget between `dst` and `onChunk`), coalesce or sample progress
events in the scheduler (per-second flush, first-N-lines + counter), and
cap TUI transcript retention for progress lines. Pin with a test asserting
total streamed bytes for a chatty command stay under the bound.

**Regression test**
Execute a command emitting 10× the cap; assert total `onChunk` bytes and
terminal transcript growth stay bounded while the final `Result` still
carries truncation metadata.

**Confidence**
High (mechanism quoted; TUI rebuild cost per prior audit, not re-measured
here — the unbounded-stream half is confirmed, the stall-rate half is
Medium).

### [P2] Headless permission prompt printed raw arguments (FIXED in this audit)

**Location**

* `internal/permissions/stdin.go:42-47` (pre-fix) — `json.MarshalIndent`
  printed without scrub.

**Problem**
`ff run` approval prompts wrote full argument JSON — including shell `env`
objects with tokens — to stdout, where pipes, `tee`, CI logs, and
supervisor captures retain them indefinitely.

**Failure scenario**
Nightly supervised run prompts (or logs the prompt) for a deploy command
carrying `DEPLOY_TOKEN`; the token lands in a log aggregator with a
90-day retention.

**Impact**
Credential exposure through logs (requirements 32, 33).

**Evidence**
Pre-fix code printed `args` verbatim; contrast with the TUI path which
scrubbed strings. Reproduced by the regression test failing pre-fix
(secret present in output) and passing post-fix.

**Fix**
Applied: `redact.Scrub` over the marshaled JSON before printing
(`stdin.go:47-52`), display-only, decision unaffected.

**Regression test**
`TestStdinAsker_ScrubsSecrets`
(`internal/permissions/stdin_cancel_test.go`): env object with `sk-…`
secret + numeric value; asserts denial decision preserved and secret absent
from output. Verified FAIL pre-fix / PASS post-fix.

**Confidence**
High.

### [P2] TUI approval modal painted non-string arguments raw (FIXED in this audit)

**Location**

* `internal/tui/permission.go:233-241` (pre-fix) — `json.Marshal(v)`
  assigned to `val` with no scrub, unlike the string branch (`:207`).

**Problem**
Any non-string argument (objects, arrays, numbers-as-JSON) — notably
`shell.env` maps — rendered credentials verbatim in the approval modal.

**Failure scenario**
Model proposes `shell` with `env: {PROD_TOKEN: "sk-…"}`; the approver's

**Impact**
Credential exposure on a display surface (requirements 32, 33).

**Evidence**

**Fix**
Applied: `val = redact.Scrub(string(raw))` before the 200-char truncation

ordering. Display-only.

**Regression test**
`TestPermissionPromptScrubsNonStringArgs`
(`internal/tui/permission_redact_test.go`): asserts the secret is gone
while non-secret content (`command`, `RETRIES`) still renders. Verified
FAIL pre-fix / PASS post-fix.

**Confidence**
High.

### [P2] `extraEnvArgs` accepts arbitrary env keys; WSL small-path passes them raw to `/usr/bin/env`

**Location**

* `internal/tools/shell/shell.go:948-968` — validates only that values
  are strings; keys never checked (`pairs = append(pairs, k+"="+s)`).
* `internal/sandbox/wsl_windows.go:187-188` — small-path appends
  `req.ExtraEnv` raw after `/usr/bin/env`.
* Contrast: large-payload path validates
  (`internal/sandbox/wsl_shared_windows.go:131-137`, `envNameRe`).

**Problem**
Model-controlled keys containing `=`, spaces, leading `-`, or empty
strings reach process setup. Natively they merge via `os.Environ`
append (weird but contained); on the WSL small path they become argv to
GNU `env`, where `-u`, `--split-string`, or `LD_PRELOAD=x` entries alter
`env` semantics rather than setting a variable. Behavior also diverges by
payload size (small accepted, large rejected), which is itself a
correctness bug.

**Failure scenario**
Prompt-injected tool call sets `env: {"-u": "PATH", "LD_PRELOAD": "…"}`
on a small WSL command; `env` interprets the flag; command runs with a
mangled environment. Separately, `PATH`/`LD_*` overwrites are accepted in
all modes with no blocklist (documented here as accepted-by-design but
unwarned).

**Impact**
Unsafe tool invocation aid; environment-confusion primitive
(requirements 26, 28, 29).

**Evidence**
Code quoted above; `envNameRe=^[A-Za-z_][A-Za-z0-9_]*$`
(`wsl_shared_windows.go:156`) exists but is enforced on only one of two
paths.

**Fix**
Validate keys with `envNameRe` in `extraEnvArgs` (single choke point covers
shell, jobs, native, and both WSL paths) returning `ArgumentError` on
mismatch; consider blocking `LD_PRELOAD`/`LD_LIBRARY_PATH`/`PATH`
overwrites or at least warning in the permission prompt's execution facts.

**Regression test**
`extraEnvArgs` table test: keys `-u`, `A=B`, `""`, `has space` rejected;
`FOO`, `_x9` accepted. WSL argv test: small-path command with hostile key
never reaches `linuxArgv` unvalidated (after fix, rejected earlier).

**Confidence**
High.

### [P2] Interactive-command heuristic has deterministic bypasses

**Location**

* `internal/tools/shell/shell.go:770-858` (lists + detection),
  `commandSeparators` (`:792`: `&&|\|\||[;|]`), `splitFields` (`:880-887`,
  splits only space/tab).

**Problem**
Four confirmed gaps: (1) no split on newline or single `&` (background),
so `"true\nvim"` / `"true & vim"` stay one segment; (2) wrapper-flag
stop: `env -i vim`, `sudo -u root vim`, `xargs -i vim` break at the flag
(`-i`/`-u`) before reaching the interactive name; (3) bare shells missed —
`bash`/`sh`/`zsh`/`fish` with no args never match (`detectInteractiveCommand`
only inspects `-c` payloads; `bareReplCommands` lacks them); (4)
`python -i` missed — `bareReplCommands[name] && i==len(fields)-1` requires
last position, so flags after the name evade. The `-c` recursion
(`:840-848`) is explicitly "deliberately simple."

**Failure scenario**
Model (or injected content) runs `env -i vim` or `python -i`;
detection misses; execution proceeds with `Stdin=nil` (EOF, no TTY), so the
likely outcome is a hung-until-timeout process burning one 300s window per
attempt — availability damage and, in aggregate over 5 days, systematic
stall. True TTY escape is still prevented by null stdin.

**Impact**
Availability + defense-in-depth erosion (requirements 26, 58). Real
containment remains `Stdin=nil` + timeout + kill + default-ask — this
heuristic is not the boundary, and must never be described as one.

**Evidence**
Each gap traced to the exact regex/condition above; wrapper list
(`sudo,env,nohup,command,xargs,nice,stdbuf,time`) lacks
`doas,su,runuser,setsid,timeout,unshare,nsenter,chroot`.

**Fix**
Split segments on newlines and single `&` (outside quotes); skip
flag-looking tokens (`-…`) after wrapper names before matching; add bare
shells without args and `python -i`-style flag-tolerant REPL matching to
the detector; extend the wrapper list. Keep `Stdin=nil` + timeout as the
stated boundary in docs. Add bypass regression tests mirroring the cases
above.

**Regression test**
Table test over `detectInteractiveCommand` (or its wrapper):
`env -i vim`, `sudo -u root vim`, `true\nvim`, `true & vim`, `bash`,
`python -i` all detected; `python script.py`, `vim file --help`… (careful:
`vim file` is intentionally blocked as always-TTY — pin that too).

**Confidence**
High for gaps 1–4 (each is a quoted condition); Medium that any gap yields
more than timeout-burn given null stdin.

### [P2] Sensitive-path escalation ignores foreground `shell`

**Location**

* `internal/runtime/scheduler.go:411-439` — `isSensitiveCall` covers
  `read_file,write_file,list_files,search_files,search_code,find_files,git,secret_scan`
  (via `path`) and `shell_job` (via `cwd`); `default: return false`
  excludes foreground `shell` and all `mcp__*` tools.

**Problem**
`shell {command: "cat ~/.ssh/id_rsa"}` and any MCP tool touching
sensitive paths never trigger forced-Ask through this path. The defense
relies entirely on shell's base default (`ask`) and on MCP adapters
claiming no `BoundaryChecker` (pinned by
`TestMCPNoBoundaryChecker`). If an operator sets shell to `allow` (or a
session Always-allow for an identical benign command — now correctly
per-command scoped, `scheduler.go:457-467`), the sensitive read executes
without escalation.

**Failure scenario**
Operator pre-allows a benign deploy command; a later identical-prefix but
exfiltrating command differs textually (correctly not covered by the
Always key) yet a broad `allow` rule for shell in config still auto-fires
on `cat $HOME/.aws/credentials`.

**Impact**
Permission-boundary gap (requirements 29, 30). Mitigated by default-ask
and per-command Always scoping — genuine protections, see below.

**Evidence**
Switch quoted above; `shell` absent while `shell_job` present.

**Fix**
Extend escalation to foreground `shell` by scanning `command` + `cwd`
with `IsSensitivePath` (lexical, fail-closed direction), and to MCP calls
by inspecting string arguments for sensitive-path shapes (or require MCP
tools to declare path-like fields). Lexical scanning of command text can
over-trigger; scope to home-relative sensitive anchors (`~/.ssh`,
`~/.aws`, `*.pem`, `.env`) to keep precision.

**Regression test**
`scheduler` permission test: `shell{command:"cat ~/.ssh/id_rsa"}` with a
permissive manager still resolves to Ask; benign `shell{command:"ls"}`
unaffected.

**Confidence**
High (absence verified); Medium on exploitability given default-ask.

### [P2] Provider headers silently override `Authorization` (secret-on-disk vector)

**Location**

* `internal/providers/openai_compatible.go:342-347`,
  `anthropic.go:308-313`, `gemini.go:275-280`, `responses.go:237-242` —
  custom `Headers` applied after the resolved API key with `Header.Set`.
* Config validation checks only header names
  (`internal/config/config.go:241-245`), never values or collisions.

**Problem**
`headers: {Authorization: …}` (or `x-api-key:` / `x-goog-api-key:`)
silently replaces the resolved key with no warning, and — worse — places a
live credential in `config.yaml`, defeating the design that secrets stay
in env/`.env` and never touch disk (`config.go:359-360`, APIKey `yaml:"-"`).

**Failure scenario**
A copied config snippet or model-suggested "fix" adds an Authorization
header; the key is now plaintext on disk, survives key rotation in the
environment, and rouges attribution when debugging auth failures.

**Impact**
Credential handling + operator footgun (requirements 32, 33, 51).

**Evidence**
All four adapters share the set-after-auth pattern; `validateEntry`
validates name tokens only.

**Fix**
Reject (fail-closed with an actionable error) header names that collide
case-insensitively with `Authorization`, `x-api-key`, `x-goog-api-key`,
`api-key` at config validation; warn loudly if any header value matches a
registered secret shape.

**Regression test**
Config validation test: headers containing `authorization` (any casing) or
`x-api-key` rejected; provider test: resolved key wins or construction
fails when colliding headers present.

**Confidence**
High.

### [P2] No global rate limiter; no trickle-body timeout

**Location**

* Retry/backoff: `internal/providers/retry.go:41-46` (3 retries, 1s/30s
  caps, 60s Retry-After cap), `transient.go:46-54` (turn-level 10s hint
  cap), `runtime.go:2314-2318` (`maxTurnRetries=2`). Per-instance
  in-flight gate: `retry.go:319-339` (fails fast with
  `errRequestInFlight`, never queues).
* Header-only timeout: `internal/providers/http.go:15-22`
  (`ResponseHeaderTimeout: 120s`, `Client.Timeout: 0` — pinned by
  `timeout_test.go:24-28`).

**Problem**
Two related availability gaps: (a) nothing coordinates request rate across
provider instances, discovery fetches, or supervisor restarts — sustained
429s are handled per-request with correct backoff+jitter+Retry-After, but a
burst of supervised restarts can re-hit a struggling provider at full
speed; (b) once headers arrive, no idle- or total-body timeout exists, so
a 1-byte-per-119s trickle holds a turn (and its context slot) forever.

**Failure scenario**
Day 2: provider degrades with slowloris-style streams; every turn hangs on
trickle bodies; supervisor sees no `ExitRetryable` (no error, just slow),
so no restart; the 5-day budget burns with zero progress. Separately, a
fleet of supervised sessions (or discovery + inference sharing one gate,
`openai_compatible.go:605-610` early-release vs `ollama.go:74-77`
hold-across-decode inconsistency) stampedes after an outage.

**Impact**
Bounded-progress failure (requirements 1, 3, 15, 20).

**Evidence**
`http.go` comment explicitly bounds headers only; `Client.Timeout=0`
asserted by test (by design, to allow long streams). No token bucket /
`x-ratelimit` parsing anywhere (grep-verified absence).

**Fix**
Add an idle-body timeout (e.g. no chunk for N seconds → transient error →
turn retry → `ExitRetryable`) while keeping total-stream unbounded; add a
process-wide token bucket or minimum-interval limiter shared by inference
+ discovery + supervised children, honoring `Retry-After` globally.

**Regression test**
Trickle-body test: stream stalling > idle cap surfaces transient error and
`ExitRetryable`; limiter test: N concurrent provider instances never exceed
configured RPS.

**Confidence**
High (both gaps are explicit code, not inference).

### [P2] Uncapped per-operation session-allow growth + in-run history growth knobs

**Location**

* `internal/runtime/scheduler.go:448-454` (`sessionAllow` map, now keyed
  per-operation `sessionAllowKey`, `:457-467` — command+cwd+envHash).
* `internal/runtime/runtime.go:1983-1991,2058,2086` (in-run `messages`
  retains full history; only the provider *view* is windowed,
  `windowForProvider`, `:1622-1631`).
* `internal/task/state.go:165-212` (counts capped at 64/64/32 but string
  fields unbounded).

**Problem**
Per-command Always scoping (correct for security) trades a bounded map for
an unbounded one: every unique shell command in a 5-day run adds a key
forever (process lifetime). In-run `messages` grows one assistant + N tool
messages per iteration up to `MaxIterations` (default 60 — bounded in
practice), but programmatic `Limits<=0` disables all caps with only a
documented-test acknowledgment, and task strings (phase/notes/verification
notes) have no length cap in memory (prompt rendering is bounded at
`task/state.go` summary truncation, memory is not).

**Failure scenario**
Thousands of distinct generated commands over 5 days → sessionAllow map
with tens of thousands of entries; a pathological model emitting unique
commands plus `Limits{0,…}` via API → multi-GB run history.

**Impact**
Bounded-but-excessive growth (requirements 10, 11).

**Evidence**
